The ground truth the link finder is scored against: every HTTP request that code in one of four Sentry repositories
sends to an HTTP route served by another of them. `answer-key.json` is the machine-readable copy.

## How it was made

1. For each repository, two independent searches listed outbound HTTP calls to the other three services: one by
   HTTP client usage, one by the settings and names that point at the other services.
2. For each call, a separate pass read the caller and found the route and handler that serve it in the target repository.
3. Two skeptics per link tried to refute it: one checked that production code really sends the request, the other that
   the route, method and handler are right. A link is in the key only if neither refuted it.
4. A completeness critic looked for missed integrations between every pair of repositories and found none.

Every link cites the exact lines on GitHub at the pinned commits. The **Checked** column records a second check on 2026-11-07: Claude re-read every cited line at the pinned commits, plus what the line alone does not show (URL prefixes, HTTP methods, how templated and payload URLs are built, the dev-only conditions). All 24 links held; the notes are in each link's `checked` field in `answer-key.json`. This is still a machine check, not a human review.

## Notes

- **snuba makes no HTTP calls to the other three.** It is only ever a target.
- **sentry makes no production HTTP calls to relay.** Events reach relay from SDKs, not from sentry's code. Its calls
  to relay's ingest endpoints exist only in tests.
- **symbolicator → sentry links have no path in symbolicator's code.** sentry builds the URLs with `reverse()`
  (`src/sentry/lang/native/sources.py`) and sends them in the request body, and symbolicator fetches whatever it is
  given. A static tool finds these only by following that data across the two repositories.
- **snuba's RPC route is one route with many endpoints.** `/rpc/{name}/{version}` is filled from `RPCEndpoint`
  subclass names; sentry's 13 call sites reach it with different names.
- `idioms.json` records how each repository declares routes and makes requests, with examples, for building the extractor.

## Score

`python -m atlas_bridge links sentry relay snuba symbolicator --alias upstream=sentry` (tree-sitter only, about
15 seconds for the four repositories on a laptop), scored with `python3 eval/score.py`:

| | Found |
| --- | --- |
| Production links | **20 / 20** |
| Dev-only links | 3 / 3 |
| Proxy (catch-all forwarding) | 0 / 1 |
| False links | **0** (precision 37 / 37) |
| Production links confirmed by SCIP | **17 / 20** (0 contradicted) |

- **SCIP** (`index`, then `links --scip-dir`) confirms every name the 17 matched production links rest on (60 name
  lookups confirmed across the run's 30 confirmed links, none contradicted), among them each hop of sentry's symbolicator chain (`_process` → `create_task` → `_request` →
  `self.session`), every `_snuba_pool` reference across modules, and relay's `UpstreamQuery` trait. L10, L19 and L20
  are inferred links, which SCIP cannot settle. Indexing took about 3 minutes for sentry (6 GB of memory) and 4 for
  relay.
- **L19, L20** (symbolicator → sentry) come out as *inferred*: sentry's `reverse()` of the route sits in code that
  builds sources for symbolicator, which fetches the URL later.
- **L10** comes out as *inferred*: sentry sends `.../subscriptions/{subscription_id}`, and the id holds
  `partition/key`, so the last parameter has to stand for two route segments.
- **L21** is missed: relay forwards any request its router does not know to its upstream. Finding it means modelling
  router fallbacks, which the extractor does not do yet.
- Three general rules keep false links out: a catch-all route that would swallow named path segments is a fallback,
  not a match; a route with fixed words must share at least one with the request; and requests made only by tests,
  CI and tooling are left out by default.


## Kafka links (`kafka-key.json`)

A second key, built the same way after the finder learned channels: two agents that never saw the finder listed every
Kafka topic one of the four repositories produces and another consumes, one from the producers and one from the
consumers, and a third merged them and tried to refute each. 31 links: sentry -> snuba 12, relay -> sentry 9, snuba -> sentry 7, relay -> snuba 3.
Score it with `python3 eval/tiny/score.py eval/sentry/kafka-key.json links.json` on the Kafka links of a run.

| Finder | Kafka links found | False Kafka links |
| --- | --- | --- |
| Library catalog only (arroyo, confluent_kafka, rdkafka, topic enums, settings maps) | 0 / 31 | 0 |
| Plus receivers named by another repository (consumers wired in a registry or YAML) | 9 / 31 | 0 |

The finder reads Sentry's producers (27 sends with resolved topic names) but no consumer in a library call: Sentry
registers its consumers in a dictionary of consumer definitions, Snuba in storage YAML (`stream_loader`), and the
topic often reaches the consumer from a command-line flag. A topic is one name on the whole broker, so a repository
that names it next to a reader's words (consume, subscribe, stream, loader, processor) and does not send to it is
taken as its consumer, as an inferred link. The nine found are Sentry -> Snuba. Not found yet: Relay's producers
(their topic names come from a Rust match on a config enum) and Snuba's producers.
